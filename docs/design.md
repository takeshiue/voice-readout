## Termux:API との関係

読み上げの実体は `termux-tts-speak` コマンドで、これは **Termux:API** という別アプリ（`com.termux.api`）が仲介して Android 標準の音声合成機能を呼び出す仕組みになっている。関係を図にすると：

```
Claude Code (Stop / Notification フック)
        │
        ▼
termux-tts-speak（Termux 側のコマンド）
        │
        ▼
Termux:API アプリ ── Android の音声合成機能を呼び出す
        │
        ▼
Google 音声認識と音声合成サービス（実際に声を合成するエンジン）
```

このプラグインは Termux:API アプリと直接連携しているため、**Termux:API アプリがインストールされていないと動作しない**。また、この経路のどこかが詰まると読み上げが止まる：

- **Google の音声合成エンジンが固まる**：エンジン自体の既知の持病。バックグラウンドで強制終了されたりクラッシュしたりする。
- **Termux:API がその「詰まった接続」を握ったまま残る**：エンジン側を直しても、Termux:API 内に壊れた接続が残っていると読み上げは復活しない。実運用では**こちらを先に強制停止する方が復旧率が高い**と分かっている。

そのため故障通知は「①まず Termux:API を強制停止 → ②直らなければ Google 音声も」の順で案内している。

## 口調を切り替える機能を持たない理由

かつて `personas/persona.md` を Haiku への指示に追記する「ペルソナ」機能があったが、2026-07-25 に削除した。口調が乗る場所が要約モードしかなかったのが理由。

- フル読み上げは本文をそのまま読むので、そもそも口調を指定する先がない。
- 許可確認・入力待ちは固定フレーズで、LLM を通さない。ペルソナ有効時は別の定型文に差し替えていたが、そちらには事前録音クリップが無いため、口調を選ぶと通知が全部ライブ合成に落ちて遅くなるという割に合わない代償があった。**通知の口調を変えたければ `assets/` のクリップを録り直せばよく、コード側の分岐は要らない。**
- 唯一効いていた要約モードでも、自由文をプロンプトに注入する構造が Haiku の拒否を招き、その拒否文がそのまま読み上げられる事故の温床になっていた（`summarize-and-speak.sh` の refusal ガードはこれを封じ込めるために生えたもの）。

## 読み上げエンジン（バックエンド）の仕組み

読み上げの音声そのものを生成するエンジンも切り替えられる。全体の設計は「4つの機能」×「TTSエンジンの4択」というマトリクスで、**機能ごとに独立してエンジンを選べる**：

| 機能 | 何を読むか | 既定のエンジン |
|---|---|---|
| ① 通知（Notification） | 許可確認・入力待ち | オンデバイス |
| ② 要約（Stop・summaryモード） | 応答を一文に要約 | オンデバイス |
| ③ フル読み上げ（Stop・fullモード） | 応答をほぼそのまま | オンデバイス |
| ④ ファイル読み上げ（`speak-text.sh`） | 任意のファイル/標準入力 | オンデバイス |

4機能とも既定はオンデバイスで、それぞれ Gemini／Inworld／ElevenLabs に個別に切り替えられる。エンジンの決まり方は次の優先順で解決される：

1. その機能専用の設定（`TTS_BACKEND_NOTIFICATION` / `_SUMMARY` / `_FULL` / `_FILE`、`toggle.sh backend-<機能>` で設定）
2. 共通の既定（`TTS_BACKEND`、`toggle.sh backend` で設定）
3. どちらも無ければオンデバイス

つまり「Gemini に切り替えて」（＝共通の既定を変更）と頼めば個別上書きしていない全機能が Gemini になり、「通知だけオンデバイスのままにして」（＝その機能だけ上書き）と頼めば通知だけ据え置ける。

**通知だけは既定をオンデバイスにしている**のは速度優先の判断（下記の速度実測を参照。以前はコードで固定していたが、切り替えたい人のために機能別設定へ移し、既定をオンデバイスにする形にした）。フル読み上げは文章が長くなりがちなので、クラウド系だと読み上げ完了までかなり長くかかる点も下記の速度実測を参照。

| | ondevice（デフォルト） | gemini | inworld | elevenlabs |
|---|---|---|---|---|
| 実体 | Android 標準 TTS（Termux:API 経由）。「ondevice」は配送経路の名前で、実際に声を合成しているのは Google のオンデバイス音声合成エンジン | Gemini API の TTS モデル（既定 `gemini-2.5-flash-preview-tts`）。音声データを `termux-media-player` 経由で Android の MediaPlayer に渡して再生する | Inworld の Realtime TTS（既定 `inworld-tts-1.5-mini`）。レスポンスがそのまま完成した WAV ファイルなので、Gemini と違い ffmpeg 変換なしで直接 `termux-media-player` に渡す | ElevenLabs（既定 `eleven_flash_v2_5`）。レスポンスが生のMP3バイト列（JSON/base64ではない）で返るので、そのままファイル保存して `termux-media-player` に渡す |
| ネットワーク | 不要（完全オフライン） | 必要 | 必要 | 必要 |
| 費用 | 無料 | Google AI Studio の無料枠内なら無料（枠を超えると課金。最新の料金は AI Studio 側で要確認） | 無料枠あり（Mini は $5/100万文字と低単価。最新の料金は Inworld の pricing ページで要確認） | 無料枠あり（月10,000クレジット≒約10分、商用不可）。最新の料金は ElevenLabs の pricing ページで要確認 |
| 故障傾向 | Google エンジン／Termux:API 側の詰まりによるハングが起きうる（開発中に繰り返し遭遇した） | Gemini 側は今のところ未検証。API 障害時は自動でオンデバイス側にフォールバックする | Inworld 側も今のところ未検証。API 障害時は自動でオンデバイス側にフォールバックする | ElevenLabs 側も今のところ未検証。API 障害時は自動でオンデバイス側にフォールバックする |
| セットアップ | 不要（インストール直後から動く） | [Google AI Studio](https://aistudio.google.com/) で API キーを取得し、`toggle.sh gemini-key <キー>` で設定する必要がある | [Inworld Portal](https://platform.inworld.ai/) で API キーを取得し、`toggle.sh inworld-key <キー>` で設定する必要がある | [ElevenLabs](https://elevenlabs.io/) で API キーを取得し、`toggle.sh elevenlabs-key <キー>` で設定する必要がある |

**API キーの保存場所**：Gemini・Inworld・ElevenLabs 共通で、プラグインのデータディレクトリの `voice-readout.env` に `KEY=値` の形式でまとめて保存される（ファイルは `600`、ディレクトリは `700`）。バックエンドが増えてもこの1ファイルにキーが集約される設計。

データディレクトリは、フック実行時は Claude Code が渡す `${CLAUDE_PLUGIN_DATA}`、それ以外（ターミナルから `toggle.sh` を叩いたときなど）は `~/.claude/plugins/data/voice-readout-voice-readout/` に解決される。**以前はこの後者が `/tmp` にフォールバックしていた**ため、上の手順どおりターミナルでキーを登録すると共有ディレクトリにキーが書かれ、しかもフック側は別のファイルを読むので登録したキーが効かない、という状態になっていた（2026-07-25 に修正）。`/tmp` にフォールバックすることはもう無い。

> **API キーはチャットに貼らないこと。** 会話に書いた内容はトランスクリプトとして端末に保存され、モデルへの入力としても送られる。キーの登録だけは**ターミナルで直接コマンドを実行する**。切替のような他の操作はチャットからで構わない。

**セットアップ手順（Gemini）**：
1. [Google AI Studio](https://aistudio.google.com/) で API キーを取得する
2. **ターミナルで** `bin/toggle.sh gemini-key <キー>` を実行する
3. 「Gemini の TTS に切り替えて」で backend を切替（裏で `toggle.sh backend gemini` を実行）

**セットアップ手順（Inworld）**：
1. [Inworld Portal](https://platform.inworld.ai/) で API キーを取得する
2. **ターミナルで** `bin/toggle.sh inworld-key <キー>` を実行する
3. 「Inworld の TTS に切り替えて」で backend を切替（裏で `toggle.sh backend inworld` を実行）

**セットアップ手順（ElevenLabs）**：
1. [ElevenLabs](https://elevenlabs.io/) で API キーを取得する
2. **ターミナルで** `bin/toggle.sh elevenlabs-key <キー>` を実行する
3. 「ElevenLabs の TTS に切り替えて」で backend を切替（裏で `toggle.sh backend elevenlabs` を実行）

登録済みのキーを消すには `bin/toggle.sh <エンジン>-key clear`（例：`bin/toggle.sh gemini-key clear`）。シェルの履歴にキーを残したくない場合は、コマンドの先頭に空白を1つ入れて実行するか、`voice-readout.env` を直接編集する。

**モデルは config、声と言語は環境変数**で上書きできる。モデルは config に集約済みで `toggle.sh tune GEMINI_MODEL <id>` / `INWORLD_MODEL` / `ELEVENLABS_MODEL` で変えられる。声と言語だけは config キーを持たず環境変数のまま：Inworld は `VOICE_READOUT_INWORLD_VOICE`（既定 `Olivia`、英語ネイティブの若い英国系女性声。Hina/Asuka/Sarah/Selene/Evelyn と聴き比べた上で2026-07-20に選定）と `VOICE_READOUT_INWORLD_LANG`（既定 `ja`）、ElevenLabs は `VOICE_READOUT_ELEVENLABS_VOICE`（既定 `blVzlvngVR9lhf4Gflnk` = アカウントのマイボイス「アマテラステラス2」、middle-aged・ja-kanto）。日本語に強い声を探したい場合は各社のダッシュボードで試聴して差し替える。

Gemini・Inworld・ElevenLabs いずれも、バックエンドが失敗した場合（キー未設定、API エラー、タイムアウトなど）は、その回だけ自動的にオンデバイスバックエンドで読み上げ直すフォールバックが入っているため、切り替えても無音になることはない。

**速度の実測（2026-07-20、4バックエンドを同一セッション内・同一文章で計測。読み上げ完了までの時間）**：

| 文章の長さ | オンデバイス | Gemini | Inworld | ElevenLabs |
|---|---|---|---|---|
| 短文（22字） | 8.8秒 | 20.8秒 | 15.9秒 | 14.6秒 |
| 中文（79字） | 16.8秒 | 39.5秒 | 26.0秒 | 25.1秒 |
| 長文（211字） | 34.4秒 | 59.9秒 | 49.9秒 | 46.5秒 |

オンデバイス比では、Gemini は1.7〜2.4倍、Inworld は1.5〜1.8倍、ElevenLabs は1.4〜1.7倍の時間がかかる。**この実測では ElevenLabs が3社中もっとも速く、僅差で Inworld、Gemini がはっきり遅い**という順序になった（公開ベンチマークでは Inworld Mini の方が Time-to-First-Audio は短いとされているが、ここでの計測は「音声が鳴り終わるまでの合計時間」で、両者の読み上げ速度・API往復のばらつきも含むため、単純な TTFA 比較とは前提が異なる点に注意）。文章が長くなるほど固定の通信コストの割合が薄まり、オンデバイスとの差は縮む傾向。この差が、許可確認の読み上げの既定をオンデバイスにしている（クラウド系にしていない）理由。

> **この表は「一度に合成して鳴らす」時代の数値である。** 現在はクラウド系も文をチャンクに割って先読みし、継ぎ目をかぶせ、フル ハイブリッドならオンデバイスが出だしを埋める。喋り出しまでの体感はこの表よりずっと短く、順位づけの意味も薄れている。残してあるのは「クラウドは総所要時間で見ればオンデバイスより遅い」という骨格が変わっていないため。
>
> エンジン選びの現在の指針は「[既定値をどのエンジンで決めるか](#既定値はエンジンごとに違う)」を参照——**無料枠でクラウドの声に手が届くのは実質 Gemini だけ**なので、速度だけで ElevenLabs を勧めるのは実態に合わない。

（旧バージョンの実測値はテスト文言が異なり単純比較できないため、上表は同条件で取り直したもの。長文の Gemini は初回計測時に `curl --max-time 20` のタイムアウトに引っかかって失敗しており、Gemini・Inworld・ElevenLabs とも45秒に緩めて計測している。）

## 読み上げ速度（全エンジン共通の指標）

速度は **`READOUT_SPEED` ひとつ**で決める。**1.0 = 毎分およそ300字**で、これはニュースを読むアナウンサーの標準的な話速にあたる。既定は **1.2**（Claude Code の出力は全部を集中して聞くものではなく、少し速い方が実用的なため）。「読み上げを1.3倍にして」「もう少しゆっくりして」のようにチャットで変えられる（裏で `toggle.sh speed 1.3`、範囲は 0.5〜2.0）。

**なぜエンジンごとの設定にしないのか**：4つのエンジンは素の話速がそもそも違うため、同じ「1.3」を各エンジンに設定しても速さは揃わない。同一文（147字）を無調整で読ませた実測（2026-07-25）：

| エンジン | 素の話速 | 300字/分との比 |
|---|---|---|
| gemini | 361字/分 | 1.20 |
| elevenlabs | 327字/分 | 1.09 |
| ondevice | 305字/分 | 1.02 |
| inworld | 271字/分 | 0.90 |

そこで各エンジンのキーは既定で `auto` とし、指標にこの差を吸収する係数を掛けて自動で決める：

| エンジン | キー | 係数 | 指標1.2 | 指標1.3 |
|---|---|---|---|---|
| ondevice | `TTS_RATE` | ×1.01 | 1.21 | 1.31 |
| inworld | `INWORLD_SPEAKING_RATE` | ×1.11 | 1.33 | 1.44 |
| elevenlabs | `ELEVENLABS_ATEMPO` | ×0.92 | 1.10 | 1.19 |
| gemini | `GEMINI_SPEED` | ×0.83 | 1.00 | 1.08 |

**厳密な倍率ではなく目安**である。同じ指標でも文章や声で数%はぶれるし、gemini だけは信号処理ではなくプロンプトでの速度指示なので追従が最も甘い。特定のエンジンだけ調整したいときは、そのキーに `auto` の代わりに数値を書けばそちらが優先される。

参考までに、オンデバイスで実測した体感の目安：指標1.0 が28.9秒（305字/分、アナウンサー相当）、1.4 が21.2秒（416字/分、早口な会話より少し速い）だった。

## 読み上げ速度の内訳（ElevenLabs）

ElevenLabs で「読み上げが遅い」と感じたときの調整方法は、**選んでいるモデルによって変わる**。2026-07-25 に同一文（55文字）・同一の声で実測した結果：

| 方法 | eleven_v3 | eleven_flash_v2_5 |
|---|---|---|
| API の `speed`（`ELEVENLABS_SPEED`） | **効かない**。1.0 / 1.2 / 1.4 とも同じ長さで、しかもエラーにならず 200 が返るため気づけない | 効く。ただし範囲は 0.7〜1.2 で、外すと 400（`invalid_voice_settings`） |
| オーディオタグ（`[rushed]` を本文の先頭に付ける） | わずかに効く（3回とも −4%前後）。`[fast-paced]` `[quickly]` `[speak quickly]` は効果なし | 未計測 |
| **`ELEVENLABS_ATEMPO`（生成後に ffmpeg で加速）** | **効く**。1.2 で −18%、1.3 で −25%、1.4 で −29% | 同じく効く |

素の速さはモデル自体でも違い、同じ文で v3 が 8.5〜8.7秒、flash が 7.4秒だった。

**推奨は `ELEVENLABS_ATEMPO`**。理由は3つ：モデルを選ばずに効く、`atempo` はピッチを変えないので声の印象が変わらない、そして**追加コストがほぼゼロ**——`ELEVENLABS_GAIN` が既定値でなければ生成後に ffmpeg を1回通っており、そこにフィルタを足すだけで済むため。値は `toggle.sh tune ELEVENLABS_ATEMPO 1.2` のように設定する（0.5〜2.0。範囲外はログに残して無視し、加工なしの音声で鳴らす）。

## クラウド読み上げのチャンク再生と継ぎ目マーカー

> 継ぎ目に実際どれだけ無音が空いているかをマイクで測った記録は [継ぎ目の実測](seam-measurement.md) にある。**現時点では判定基準の1.5秒を満たした回は無く、マーカー検出が安定していないため実測値そのものがまだ確定していない。**

クラウド系（Gemini／Inworld／ElevenLabs）は、長い文章を一度に合成すると生成が終わるまで無音の待ち時間になる。そこで**文章を文単位でチャンクに分け、1つ目が出来たらすぐ喋り始め、喋っている裏で次を生成する**（先読み）。さらに、次のチャンクの再生開始を現在のチャンクの終わりに**少しかぶせて**呼び出すことで、`termux-media-player` の起動往復（実測で約2秒）を鳴っている音の裏に隠している。

| KEY | 既定 | 何が変わるか |
|---|---|---|
| `CLOUD_FIRST_CHUNK_CHARS` | 80 | **1つ目**のチャンクの長さ。短いほど喋り出しが早い |
| `CLOUD_SECOND_CHUNK_CHARS` | 120 | **2つ目**のチャンクの長さ。下の「最初の継ぎ目だけ余裕がない」を参照 |
| `CLOUD_CHUNK_CHARS` | 200 | 3つ目以降のチャンクの長さ。長いほど継ぎ目の回数が減る |
| `CLOUD_PLAY_LEAD` | auto | 次のチャンクを何秒早くかぶせるか。**足りないと継ぎ目に隙間**が空き、大きすぎると語尾が食われる。`auto` はこの端末で実測して決める（下記） |

### CLOUD_PLAY_LEAD の自動校正

かぶせるべき時間は `termux-media-player` の往復とループの処理時間の合計で、これは**端末の性質**（Termux:API の応答、CPU、Android のバージョン）であってエンジンの性質ではない。開発機での実測は2.1〜3.2秒だが、これを定数として配ると、他の端末では単純に間違った値になる。しかも利用者にはその値の存在も、正しい測り方も分からない。

**学習期間中は 2.2秒で動く。** 何も測っていない状態に置かれる無難な仮値ではなく、開発機で実測した値を初期値として入れてある。学習期間は数回の読み上げにわたり、その間ずっと利用者は音を聞いているので、誰も測っていない値で数分間ぶんの継ぎ目を悪くする理由がない。3つのクラウドバックエンドすべてで測った往復1.8〜2.0秒とも同じ桁で、仮に相手の端末がもっと速くても、**小さすぎる側に外れれば短い無音が残るだけで、大きすぎる側のように語尾は食わない**（安全な方向に外れる）。

そこで**学習期間**を設けて実測する。継ぎ目ごとに「使った lead ＋ 空いた隙間」＝本来隠すべきだった時間を1サンプルとして貯め、`CLOUD_PLAY_LEAD_SAMPLES`（既定24）に達したら値を**一度だけ**書いて確定する。以後は計算も書き込みも起きない。読み上げ1回で3〜7サンプル貯まるので、5〜10回で終わる。

- **なぜ毎回追従させないのか**：追従させると、たまたま端末が重かった1回が次の lead を過大にし、**次のチャンクの語尾を食う**。それに毎回変わる値は「端末の性質」ではない。
- **なぜ平均ではないのか**：採用するのは**平均 − 平均偏差**。誤差の代償が非対称で、小さすぎれば文の切れ目に短い無音が残るだけだが、大きすぎると音節が消える。往復時間は下限がはっきりある一方で遅い側に長い尾を引くため、平均は下限より上に居座り、調子のいい回では必ず食う側に外れる。この式なら、安定した端末では偏差が縮んで真の値に寄り、不安定な端末では自動的に安全側へ下がる。
- **利用者の意思が優先**：`CLOUD_PLAY_LEAD` に数値が入っていれば、それがそのまま使われ、学習も行われない。
- **やり直し**：「校正をやり直して」（`toggle.sh recalibrate`）で確定値を捨て、学習期間が再開する。
- **通知**：確定したときに一度だけ、次のセッション開始時に画面へ一行出る（測定値と、やり直し方）。学習中は何も出さない。

### 既定値はエンジンごとに違う

調整値のうち「エンジンの性質」を表すものは、`KEY_<エンジン名>` の形で分けて持てる（優先順位は `KEY_<エンジン名>` ＞ `KEY` ＞ 内蔵の既定値）。そして**内蔵の既定値自体もエンジンごとに変えてある**：

| KEY | gemini | 他 | なぜ |
|---|---|---|---|
| `HYBRID_MIN_ONDEVICE_CHARS` | 60 | 0 | 1本目の生成に6〜10秒かかるので、その間オンデバイスに読ませて助走を確保する |
| `HYBRID_PREGEN_CHUNKS` | 3 | 2 | 生成が再生の0.8〜1.0倍で余裕が薄いため、1本多く作り置く |
| `CLOUD_SECOND_CHUNK_CHARS` | 200 | 120 | 6秒前後の固定の立ち上がりがあるので、短く割ると割った回数だけその固定費を払う |

**なぜ Gemini を基準に既定値を決めるのか**：ここで測った数値はどれも ElevenLabs で測ったものだが、ElevenLabs を選ぶ人はほとんどいない。無料枠が月10分程度で商用不可なので、選ぶ＝課金するということになる。Inworld はそもそも存在を知られていない。**無料枠でクラウドの声に手が届くのは Gemini だけ**で、しかも Gemini は3つの中で一番条件が厳しい（生成が再生の0.8〜1.0倍、立ち上がり6〜10秒）。既定値を ElevenLabs のままにすると、「無料のクラウド音声を使いたい」と思って入れた人が、自分の使っていないエンジンで測られた値で動き始めることになる。しかもその人には値の存在も測り方も分からない。

### 最初の継ぎ目だけ余裕がない

2つ目のチャンクの生成を隠せるのは1つ目の再生時間だけで、その1つ目は喋り出しを早くするためにわざと短く切ってある。3つ目以降は「2チャンク分の再生時間」が次の生成を覆うので事情がまったく違う。実測（2026-07-28、ElevenLabs v3、1174字の同一テキスト）:

| 2つ目の長さ | 2つ目の余裕 | 3つ目の余裕 |
|---|---|---|
| 197字（上限なしの頃） | **+0.8秒** | +33.1秒 |
| 118字（`CLOUD_SECOND_CHUNK_CHARS=120`） | **+8.2秒** | +22.5秒 |

余裕0.8秒は「たまたま間に合っている」状態で、実際に隙間として聞こえた回がある。2つ目を短くすると3つ目以降の再生開始が前倒しになるぶん、3つ目の余裕は削られる（33→22秒）が、生成時間は再生時間の約0.55倍なので後続は元々桁違いに余っている。**律速は常に2つ目**で、そこだけ中間の長さを挟むのが `CLOUD_SECOND_CHUNK_CHARS` の役割。

### 生成が途中で切れて返ってくることがある

バックエンドが「テキストの途中までしか読んでいない音声」を返すことがある（2026-07-28、Gemini で実測：読むのに25.2秒かかるはずの184字が16.8秒で返り、文の3分の1が消えていた）。レスポンス自体はエラーではなく、正当な・完結した短いファイルとして返るので、何も見ずに再生すると文の途中で読み上げが終わる。

判断材料は長さしかない。プラグインは全エンジンに `READOUT_SPEED` で話速を指示しているので、**その話速で読み切るのに必要な時間に対して音声が短すぎれば作り直す**（`CLOUD_MIN_AUDIO_RATIO`、既定0.65で1回だけ再生成）。閾値をわざと緩くしてあるのは、エンジンは指示した話速より5〜30%速く読むうえ、実際に切れていた2例が59%・60%だったのに対し健全なものは79〜98%だったため。緩く外せば余分な生成が1回増えるだけだが、きつく張ると聞き手が文の終わりを失う。

### チャンク区切りマーカー

`CHUNK_MARKER`（既定 off）は、この継ぎ目を調整するための確認用の機能。on にすると各チャンクの末尾に短いキュー音（`assets/chunk-marker.wav`、0.78秒）が鳴る。

- **何のためにあるか**：音だけ聞いていると、聞こえた“間”が**文の切れ目でそう喋っただけ**なのか、**チャンクの受け渡しで空いた隙間**なのか区別できない。マーカーを入れると並びが `[本文][ピッ][間][次の本文]` になり、**ピッの直後に空いた間だけが継ぎ目の隙間**だと確定できる。`CLOUD_PLAY_LEAD` を上げるべきかどうかは、この区別が付いて初めて判断できる。どこで分割されたかを知る手段が他にないので、チャンク長を変えるときの目安にもなる。
- **使い方**：「チャンクマーカーをオンにして」で on（裏で `toggle.sh chunk-marker on`）。on の間はステータスラインの末尾に 🔔 が出るので、鳴っている理由が分からなくなることはない。
- **コスト**：キュー音そのものが0.78秒×チャンク数ぶん再生時間を延ばす（これが主観的には支配的）。処理としては生成直後に ffmpeg で音声へ連結するため0.3〜0.45秒/チャンクかかるが、2つ目以降は前のチャンクを再生している裏で走るので体感には出ない（1つ目だけ喋り出しが0.3秒ほど遅くなる）。
- **実装（なぜ別再生ではなく連結なのか）**：キュー音を別ファイルとして再生すると、`termux-media-player` の起動往復（約2秒）がそのまま「本文とキュー音の間の空白」になり、何を測っているのか分からなくなる。生成したチャンク音声の末尾に連結して**同じ再生の続き**として鳴らすことで、この遅延を排除している。
- **対象**：クラウド系のチャンク再生経路のみ。オンデバイスや固定クリップには入らない。

## フル ハイブリッド（出だしはオンデバイス、続きはクラウド）

クラウド音声は良いが、最初の音が出るまでが遅い。生成に数秒、その音を鳴らす `termux-media-player` の往復にさらに約2秒かかる。一方オンデバイスのエンジンは約3秒で喋り出し、ネットワークも要らない。**フル ハイブリッド**（`HYBRID_TTS`、既定 off）はその差を使う。出だしをオンデバイスで読んでいる間にクラウド音声を作り、間に合った時点で声を交代する。

「フル読み上げ」かつ「そのバックエンドがクラウド」のときだけ効く。要約や通知には効かない（一文ぶんの短さでは、声が変わる違和感に見合うだけの短縮にならない）。ステータスラインでは `resp 🔊 full hyb inworld` のように、実際に効く条件が揃っているときだけ `hyb` が出る。

**交代地点は事前に決めない。** 早すぎればクラウドが間に合わず無音になり、遅すぎればオンデバイスの声を必要以上に聞かされる。そこで本文を小さな**ユニット**（既定60字＝約11秒）に刻み、ユニットの境目ごとに「クラウドはもう出来ているか」を確認して、最初に「出来ている」と答えた地点で交代する。ユニットの途中では切り替えない（読み上げ中のエンジンを止めるのが、Termux:API のエンジンを固まらせる既知の引き金）。

先行生成しているのは「次のチャンク」ではなく「**その境界から先の全部**」で、候補どうしは中身が重なる：

```
本文:      [ユニット0][ユニット1][ユニット2 ...................]
候補1              └─ ここから先をクラウドが読む
候補2                        └─ ここから先をクラウドが読む
```

候補1にはユニット1が含まれ、候補2には含まれない。候補2が使えるのは、その間にオンデバイスがユニット1を読んだからで、これが「同じ文を二度読む／一文飛ばす」を構造的に防いでいる。

境界に到達してもクラウドが返っていなければ、**無音で待たずに次のユニットを読み進める**。作りかけだった候補は捨て、ひとつ先の境界に候補を張り直す（読み進めるユニットの約11秒がそのまま新しい候補の猶予になる）。捨てた候補の音声は使わないまま破棄される。この張り直しで足りるのは「クラウドの生成時間 < ユニット1つの読み上げ時間」の間で、実測ではどのバックエンドもそこに収まる。恒常的に間に合わないなら `HYBRID_UNIT_CHARS` を上げるか、`HYBRID_SPECULATION` を 2 にして候補に1単位ぶん長い猶予を与える。

- クラウド側が**失敗**（キー無し・圏外・APIエラー）した場合は「まだ」ではなく「無理」と判定し、その場でハイブリッドを畳んで残りをオンデバイスで読み切る
- オンデバイスで読んだ累計が `HYBRID_MAX_ONDEVICE_CHARS` を超えてもクラウドが来ないときは、**読み進めるのをやめて待つ**。長くオンデバイスを回し続けること自体がエンジンを固まらせる原因なので、数秒の無音より安い
- 逆に `HYBRID_MIN_ONDEVICE_CHARS` は「最低これだけは読ませる」下限で、1本目の生成が遅いエンジン（Gemini）に助走を与えるためにある
- 交代時にはすでに出来ている音声をクラウド側パイプラインの1つ目のチャンクとしてそのまま渡すので、交代の瞬間に生成待ちは発生しない
- **交代の段取りも先に済ませてある。** 音声が出来ていても、チャンク分割・一時ファイルの掃除・ウェイクロックの解放は数秒かかり、そのまま置くと全部が「オンデバイスが黙ってからクラウドが鳴るまで」の無音に乗る（実測7秒）。分割と掃除は先行生成と同じ裏側の処理でユニットを読んでいる間に終わらせ、ウェイクロックは読み上げ1本を通して持ったまま最後にまとめて解放する
- 声が一度変わる。境目は文・句の切れ目なので単語の途中で切れることはないが、話速の印象はエンジン間で違う（`READOUT_SPEED` は全エンジンに効く共通指標なので、まずそれで合わせる）

### オンデバイスからクラウドへの継ぎ目を先読みで隠す

上の段取りを全部済ませても、継ぎ目には `termux-media-player` の `play` 往復（実測1.9秒）だけが残る。**これは安くならない**：あらかじめトラックを用意しておいて後から再開する方式も試したが、準備済みトラックの resume でも1.8〜2.2秒かかった（2026-07-27 実測）。つまりコストは MediaPlayer の prepare ではなく Termux:API の往復そのもので、置き場所を変えるしかない。置ける場所は一つしかない——**オンデバイスの声の下**。

そこで、クラウド候補が先に出来ていれば、オンデバイスがまだ喋っている最中に `play` を発行する（`HYBRID_PREPLAY_LEAD`、既定1.0秒前）。ただし `termux-tts-speak` は終わるまで何も報告しないので、「まだ喋っているか」は**観測できず予測するしかない**：

- 所要時間は「固定の立ち上がり ＋ 文字数 ÷ 速度」で見積もる（`ONDEVICE_START_SECS` 4.6秒 ＋ `ONDEVICE_CHARS_PER_SEC` 5.0字/秒）。2項に分けてあるのは、立ち上がり（Termux:API の往復＋エンジンが最初の音節を出すまで）が文字数に比例しないため。ハイブリッドのユニットは26〜60字と短く、1本の長文から求めた「5.3字/秒」だけのモデルでは数秒足りなかった。
- 既定値は実測の**平均ではなく、ほぼ全サンプルの上側を通る線**にしてある。誤差の代償が非対称だからで、**遅く見積もれば隠せなかった継ぎ目が元通り現れるだけ**だが、**速く見積もると2つの声が同時に鳴る**（TTS エンジンとメディアサービスは独立した出力なので、平気で同時に鳴る。2026-07-28 に、11.5秒と見積もった発話が17.1秒かかって実際に事故になった）。
- 見積りを安全側に倒せるのは、待ちが**「見積り時間」と「実際に声が終わったこと」のどちらか早い方**で終わるようになったから。以前は固定の sleep で待っていたため、長すぎる見積りは `play` を声の終わりより後ろに押しやり、**何もしないときより継ぎ目を広げていた**。
- 見積りは**最初の音節から**数える。`speak()` は事前確認・ウェイクロック・分割に数秒使うので、呼び出し時点から数えるとその分だけ早く撃ってしまう（2026-07-28、7秒間2つの声が重なった）。
- **端末が寝ていたら先読みしない**（`HYBRID_PREPLAY_MAX_IDLE`、既定600秒）。危険なのは TTS エンジンが冷えることではない——6分アイドル後でも8.27秒対8.15秒で無劣化だった（2026-07-27 実測）。危険なのは**端末が doze に入ること**で、17分アイドルで見積り+0.8秒、91分アイドルで**+9.5秒**。後者なら、オンデバイスの文の9秒手前でクラウドが喋り出していた。
- この窓に `WARM_SKIP_WINDOW` を流用していない理由：あちらは「事前確認を省くか」の判断で、頻繁に固まるエンジン相手に窓を広げるとハングの発見が遅れる。似ているのは見た目だけで、天秤にかけている相手が違う。

## オンデバイス読み上げの長さ制限

オンデバイス（Termux:API 経由の Android TTS）には**1回の読み上げにつき 240 文字という上限**を設けている。エンジンに渡す前にテキスト長をチェックし、超えていればエンジンには触れない。

理由は Termux:API の既知の持病（[termux/termux-api#244](https://github.com/termux/termux-api/issues/244)、2018年から未修正）で、**長い読み上げの途中でエンジンが固まり、以降すべての termux-api コマンドがハングして、アプリを手動で強制停止するまで復旧しない**。チャンク分割・バックオフ・ウェイクロック・同時実行の排除など、こちら側でできる対策は 2026-07-20 に一通り試したがそれでも固まる。復旧にユーザーの物理操作（強制停止）が要る以上、**そもそも固まる領域に入らない**のが唯一まっとうな設計になる。この端末での実測では、同じ文章を3回読ませて 250 文字は毎回完走、336 文字は毎回同じチャンクで失敗した。240 文字（約45秒）は既知の安全圏の内側に余裕を持たせた値。

上限を超えたとき、**オンデバイスを選んでいる機能はオンデバイスのまま**、一文に要約して読み上げる。その際「**長文のため要約にします。**」という短い断りを先に流してから要約を伝えるので、聞き手は全文ではなく要約を聞いていることが分かる。この断りは**決まり文句なので事前に良い声（Gemini/Aoede）で録音した音声を同梱**していて（`assets/overflow-notice.wav`）、実行時はそれを `termux-media-player` で再生する（API キー不要）。同梱音声が無い環境では断り文をライブTTSで読み上げてフォールバックする。フル読み上げ・ファイル読み上げのどちらも同じ扱い：

| 機能 | オンデバイスで上限超過したとき |
|---|---|
| フル読み上げ（Stop・full） | 断りを添えて**一文要約に劣化**して読む。要約自体が240字を超える場合は240字に切り詰める |
| ファイル読み上げ（`speak-text.sh`） | 断りを添えて**一文要約に劣化**して読む（全文を読むには下記のとおりクラウド系へ切替） |

**上限超過でクラウドへ自動切替はしない**。オンデバイスを選んでいるのは利用者の明示的な選択であり、クラウドのAPIキーが登録されていてもそれを勝手に上書きはしない——クラウドの声を使いたい人は自分で切り替える、という考え方（機能ありきの一貫した扱い）。

クラウド系バックエンド（Gemini／Inworld／ElevenLabs）にはこの上限は無い。**長文を丸ごと読ませたい場合は、その機能のエンジンを自分でクラウド系に切り替える**（例：ファイル読み上げなら `toggle.sh backend-file elevenlabs`）。断り文は環境変数 `VOICE_READOUT_OVERFLOW_NOTICE` で差し替えられる（同梱クリップが無いときのライブ読み上げに使われる）。

## 長文パイプライン（冒頭を先に読み、裏で要約する）

上の「上限超過で一文要約に劣化」は、要約が出来上がるまで無音になるという弱点がある。要約は Haiku を `claude -p` で呼ぶので、CLI の起動込みで**十数秒**かかり、その間ずっと黙ったままになる。「反応がない、壊れた」と思わせるには十分な長さである。

`OVERFLOW_PIPELINE` を on にすると、その待ち時間を読み上げで埋める：

1. 応答の**冒頭 `OVERFLOW_OPENING_CHARS` 文字（既定150字）をそのまま即座に読み始める**（要約を待たないので無音がゼロになる）。区切りは直前の `。！？、` まで戻すので語の途中で切れない
2. その裏で**応答全体**を要約する（冒頭を除いた残りではなく全体。狙いは全体像であり、完全な文章から作ったほうが要約の質が高いため）
3. 事前録音クリップ「この後、全体を要約するね。」（`assets/summary-bridge.wav`）を挟む
4. 出来上がった要約を読む

3つの読み上げは**逐次**実行されるので、単一の TTS エンジンを取り合って固まることはない（並行するのはエンジンを使わない `claude` の呼び出しだけ）。冒頭を読むことでエンジンが温まり、後続がウォームスキップ（`WARM_SKIP_WINDOW`）の恩恵を受ける副次効果もある。

既定は off。実機での所要時間は `[info] pipeline timing:` のログ行（`要約 N秒 / 冒頭+ブリッジ N秒 / 要約前の空き N秒`）で確認でき、「要約前の空き」が大きければ `OVERFLOW_OPENING_CHARS` を増やす。

## 決まり文句の事前録音音声

内容が変わらない“決まり文句”は、毎回オンデバイスの機械的な声で合成する代わりに、**Gemini の良い声で一度だけ録音した WAV（`assets/*.wav`）を再生**している。狙いは、①毎回同じ良い声にする、②API キーもネットワークも使わない（録音済みなのでオフラインで鳴る）、③固まりやすい TTS エンジンを使わずに済ませる、の3つ。

- **対象の決まり文句**：上限超過の断り（`長文のため要約にします。`）／通知の定型フレーズ（`実行許可を求めています` `実行許可の確認が待っています` `入力を待っています` `確認が必要です`）／復旧メッセージ（`読み上げ、直ったみたいよ…`）／終了時の挨拶（`お疲れ様。またね。`）。
- **声**：Gemini の `Aoede`。「20歳くらいの明るいアナウンサー」というキャラクター指定プロンプトを本文の前に付けて生成している（この指定文は読み上げられず、本文だけ喋る）。
- **再生する条件**：その機能のバックエンドが**オンデバイス（既定）のときだけ**クリップを再生する。クラウド系を選んでいる場合は利用者の声の選択を尊重してライブ合成する。クリップが同梱されていない環境では、いずれもライブ TTS にフォールバックする。
- **対象外**：ツール名を含む許可メッセージはツール名が可変なので、名前を言わない汎用クリップ `実行許可を求めています` で代用している。
- **録音の作り直し**：Gemini の API キーを設定した上で、テキストと声・キャラクター指定を与えて `assets/*.wav` を再生成できる（生成は開発時に手作業で行い、できた WAV をリポジトリに同梱する）。

## ストップスイッチが設定を一切見ない理由

読み上げが暴走しているとき、ユーザーは画面を見ず**耳だけで**状況に対処していることが多い。そのため、他のどの仕組みよりも確実に効く独立したスイッチを用意している。`bin/readout-switch.sh` と `speak()` 冒頭の1行だけの、コードベースの中で最も単純な仕掛け。

**なぜ他の設定を全部無視するのか**：ストップスイッチは**固定の絶対パス** `~/.voice-readout-stopped`（Termux 側のホーム）にファイルが1つあるかどうかだけを見る。このパスは `CLAUDE_PLUGIN_DATA` から組み立てていない——その環境変数を差し替えることが、通常のトグルを迂回してしまう典型的な経路だからだ。判定は `speak()` の**いちばん最初**、設定を読むよりも、オン/オフのトグルよりも、バックエンドを決めるよりも前に行う。ファイルがあれば、何があっても喋らない。

**Termux とコンテナの境界**：通知ボタンの操作は Termux 側で実行され、そこからはこのコンテナの中（`/root`）は見えない。止めたい対象そのものに依存するスイッチは、スイッチとして成立しない。そのため `readout-switch.sh` は、Termux のホームに自己完結した小さなトグルスクリプト（`~/.voice-readout-switch.sh`）を設置し、通知ボタンはそれを実行する。ボタンはファイルを切り替えると同時に**通知を逆の状態で出し直す**（初期の版は単純な touch/rm で、ラベルが古いまま残って「停止中なのに再開ボタンが無い」状態にユーザーを取り残してしまった）。

**できないこと**：**いま喋っているチャンクは必ず最後まで鳴る**。停止は次のチャンクの直前で効き、残りを破棄する。発話中のオンデバイス呼び出しを SIGKILL すると読み上げエンジンが固まり、アプリを手動で強制停止するまで復旧しない（[長さ制限](#オンデバイス読み上げの長さ制限)と同じ持病）。途中で切るコストの方が大きいので、飛んでいるチャンクだけは鳴らしきる設計にしている。

## ステータスラインの自動登録と自動修復

`statusLine` はプラグインのコンポーネントではなく `~/.claude/settings.json` の設定項目なので、プラグインを入れただけでは登録されない。かといって利用者に絶対パスを手で書かせるのは現実的でないため、フックから登録している。

- **自動登録の仕組み**：プラグインのインストールを知らせるイベントは Claude Code に無いので、SessionStart フック（`statusline.sh --repair`）が「このプラグインのデータディレクトリにマーカーが無い＝入れたばかり」を初回の合図として使う。登録するのは `statusLine` が**未登録のときだけ**で、既に何か入っていれば触らない。マーカーはデータディレクトリごと消えるため、入れ直したときは改めて登録される。
- **登録したその起動で表示させる仕掛け**：素直に書き込むだけだと、表示が出るのは*さらに次*の起動だった（起動が合計3回必要だった）。Claude Code は `settings.json` を監視していて再起動なしに反映するが、SessionStart フックが走るのは「設定を読み終えた後・監視が始まる前」の隙間で、肝心の初回登録の書き込みだけが誰にも見られずに素通りするため。対策として、登録に成功したら切り離したワーカー（`statusline.sh --nudge`）が**約1・2・4・8・16・32秒後に同じ内容を書き直す**。監視が動き出した後の最初の1回が効いて表示が出る。残りは中身の変わらない読み直しで、実害はない。秒数を決め打ちにしないのは、起動にかかる時間が端末次第（低速なディスクへの初回展開と、温まった状態での再起動は別物）だから。この30秒の間に `--uninstall` や手編集で登録が別物になったら、そこで打ち切る。
- **個人設定に書く理由**：プラグインは全セッションで有効なので表示も全セッションに要る。またプロジェクトの `.claude/settings.json` は git で共有されることが多く、そこに端末固有の絶対パスを書くと他の人の環境を壊す。そのプロジェクトの設定に `statusLine` があると**そちらが優先される**（キー単位で上書きされるため）ので、カレントディレクトリにそれを見つけた場合は警告を出す。
- **`"command": "${CLAUDE_PLUGIN_ROOT}/bin/statusline.sh"` と書いてあると、何も表示されない。** フックはこの書き方で登録するので手が滑りやすいが、statusLine はプラグインのコンポーネントではないためこの変数は展開されず、`/bin/statusline.sh` の実行に失敗して**エラーも出ずに黙る**。`--install` はこれを自分の壊れた登録と認識して絶対パスに直す（`--force` は要らない）。
- **マーケットプレイス経由で入れた場合、更新するとプラグインの置き場所（バージョン番号を含むパス）が変わる。** これは起動時に自動で直る：SessionStart フックが `statusline.sh --repair` を実行し、登録されているパスが古ければ書き直す（**未登録なら何もしない**＝勝手に登録はしない。他のスクリプトを指していれば触らない。値が正しければ書き込まない）。直した場合はログに `[info] statusline: repaired stale path ...` が残る。旧バージョンのディレクトリは Claude Code が14日後に自動削除するため、**更新直後は古いパスのまま動き、しばらく経ってから突然表示が消える**。自動修復はこの遅れて出る壊れ方を防ぐためのもの。
- 書き換え前に `settings.json.bak-voice-readout` を残す。書き込み先を変えたい場合は `--file <パス>`。

手で書く場合はこの形（`${CLAUDE_PLUGIN_ROOT}` はここでは展開されないので絶対パスで）：

```json
"statusLine": { "type": "command", "command": "/絶対パス/voice-readout/bin/statusline.sh" }
```

## 挨拶が起動は生 TTS・終了はクリップな理由

同じ「挨拶」でも、起動時と終了時では目的が逆なので実装も逆になっている。

**起動時（`bin/session-greet.sh`）は生の TTS を通す。** 目的が「今この端末で読み上げが使える状態か」の確認だから。事前録音クリップだと TTS エンジンが死んでいても鳴ってしまい、確認にならない。挨拶が鳴らずに失敗した場合は、通常の読み上げ失敗とまったく同じ**故障通知＋自動復旧ウォッチャー**が起動時点で走る。長期アイドル明けの“エンジンが冷えて固まりやすい最初の1回”を、最初の応答ではなく起動時という予測可能なタイミングに前倒しできる副次効果もある。

**終了時（`bin/session-farewell.sh`）は事前録音クリップを鳴らす。** 終了時の挨拶に確認の目的はなく、むしろ**セッションが閉じる瞬間に確実に鳴り切ること**が重要。生 TTS はエンジン往復に数秒かかり、プロセス終了で途中で切れうる。事前録音クリップなら `termux-media-player` が Android のメディアサービスに再生を委ねるため、**このフックのプロセスが終了処理で閉じても再生は最後まで続く**（実機で検証済み）。TTS エンジンの固まりにも左右されない。

**製品名をカタカナで書いているのも意図的**で、**英字の `voice-readout` を渡すと TTS が「レッドアウト」と読む**（`read` は発音が2通りある単語で、`readout` を辞書に持たないエンジンは `read` + `out` に分解し過去形の /red/ を選ぶ）。文言を差し替えるときも同じ理由でカタカナ表記を勧める。
