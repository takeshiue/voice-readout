## Termux:API との関係

読み上げの実体は `termux-tts-speak` コマンドで、これは **Termux:API** という別アプリ（`com.termux.api`）が仲介して Android 標準の音声合成機能を呼び出す仕組みになっている。関係を図にすると：

```
Claude Code (Stop / Notification フック)
        │
        ▼
termux-tts-speak（Termux 側のコマンド）
        │
        ▼
Termux:API アプリ ── Android の音声合成機能を呼び出す
        │
        ▼
Google 音声認識と音声合成サービス（実際に声を合成するエンジン）
```

このプラグインは Termux:API アプリと直接連携しているため、**Termux:API アプリがインストールされていないと動作しない**。また、この経路のどこかが詰まると読み上げが止まる：

- **Google の音声合成エンジンが固まる**：エンジン自体の既知の持病。バックグラウンドで強制終了されたりクラッシュしたりする。
- **Termux:API がその「詰まった接続」を握ったまま残る**：エンジン側を直しても、Termux:API 内に壊れた接続が残っていると読み上げは復活しない。実運用では**こちらを先に強制停止する方が復旧率が高い**と分かっている。

そのため故障通知は「①まず Termux:API を強制停止 → ②直らなければ Google 音声も」の順で案内している。

## 口調を切り替える機能を持たない理由

かつて `personas/persona.md` を Haiku への指示に追記する「ペルソナ」機能があったが、2026-07-25 に削除した。口調が乗る場所が要約モードしかなかったのが理由。

- フル読み上げは本文をそのまま読むので、そもそも口調を指定する先がない。
- 許可確認・入力待ちは固定フレーズで、LLM を通さない。ペルソナ有効時は別の定型文に差し替えていたが、そちらには事前録音クリップが無いため、口調を選ぶと通知が全部ライブ合成に落ちて遅くなるという割に合わない代償があった。**通知の口調を変えたければ `assets/` のクリップを録り直せばよく、コード側の分岐は要らない。**
- 唯一効いていた要約モードでも、自由文をプロンプトに注入する構造が Haiku の拒否を招き、その拒否文がそのまま読み上げられる事故の温床になっていた（`summarize-and-speak.sh` の refusal ガードはこれを封じ込めるために生えたもの）。

## 読み上げエンジン（バックエンド）の仕組み

読み上げの音声そのものを生成するエンジンも切り替えられる。全体の設計は「4つの機能」×「TTSエンジンの4択」というマトリクスで、**機能ごとに独立してエンジンを選べる**：

| 機能 | 何を読むか | 既定のエンジン |
|---|---|---|
| ① 通知（Notification） | 許可確認・入力待ち | オンデバイス |
| ② 要約（Stop・summaryモード） | 応答を一文に要約 | オンデバイス |
| ③ フル読み上げ（Stop・fullモード） | 応答をほぼそのまま | オンデバイス |
| ④ ファイル読み上げ（`speak-text.sh`） | 任意のファイル/標準入力 | オンデバイス |

4機能とも既定はオンデバイスで、それぞれ Gemini／Inworld／ElevenLabs に個別に切り替えられる。エンジンの決まり方は次の優先順で解決される：

1. その機能専用の設定（`TTS_BACKEND_NOTIFICATION` / `_SUMMARY` / `_FULL` / `_FILE`、`toggle.sh backend-<機能>` で設定）
2. 共通の既定（`TTS_BACKEND`、`toggle.sh backend` で設定）
3. どちらも無ければオンデバイス

つまり「Gemini に切り替えて」（＝共通の既定を変更）と頼めば個別上書きしていない全機能が Gemini になり、「通知だけオンデバイスのままにして」（＝その機能だけ上書き）と頼めば通知だけ据え置ける。

**通知だけは既定をオンデバイスにしている**のは速度優先の判断（下記の速度実測を参照。以前はコードで固定していたが、切り替えたい人のために機能別設定へ移し、既定をオンデバイスにする形にした）。フル読み上げは文章が長くなりがちなので、クラウド系だと読み上げ完了までかなり長くかかる点も下記の速度実測を参照。

| | ondevice（デフォルト） | gemini | inworld | elevenlabs |
|---|---|---|---|---|
| 実体 | Android 標準 TTS（Termux:API 経由）。「ondevice」は配送経路の名前で、実際に声を合成しているのは Google のオンデバイス音声合成エンジン | Gemini API の TTS モデル（`gemini-2.5-flash-preview-tts` 等）。音声データを `termux-media-player` 経由で Android の MediaPlayer に渡して再生する | Inworld の Realtime TTS-1.5 Mini（`inworld-tts-1.5-mini`）。レスポンスがそのまま完成した WAV ファイルなので、Gemini と違い ffmpeg 変換なしで直接 `termux-media-player` に渡す | ElevenLabs の `eleven_flash_v2_5`。レスポンスが生のMP3バイト列（JSON/base64ではない）で返るので、そのままファイル保存して `termux-media-player` に渡す |
| ネットワーク | 不要（完全オフライン） | 必要 | 必要 | 必要 |
| 費用 | 無料 | Google AI Studio の無料枠内なら無料（枠を超えると課金。最新の料金は AI Studio 側で要確認） | 無料枠あり（Mini は $5/100万文字と低単価。最新の料金は Inworld の pricing ページで要確認） | 無料枠あり（月10,000クレジット≒約10分、商用不可）。最新の料金は ElevenLabs の pricing ページで要確認 |
| 故障傾向 | 今日ずっと対処してきたハング（Google エンジン／Termux:API 側の詰まり）が起きうる | Gemini 側は今のところ未検証。API 障害時は自動でオンデバイス側にフォールバックする | Inworld 側も今のところ未検証。API 障害時は自動でオンデバイス側にフォールバックする | ElevenLabs 側も今のところ未検証。API 障害時は自動でオンデバイス側にフォールバックする |
| セットアップ | 不要（インストール直後から動く） | [Google AI Studio](https://aistudio.google.com/) で API キーを取得し、`toggle.sh gemini-key <キー>` で設定する必要がある | [Inworld Portal](https://platform.inworld.ai/) で API キーを取得し、`toggle.sh inworld-key <キー>` で設定する必要がある | [ElevenLabs](https://elevenlabs.io/) で API キーを取得し、`toggle.sh elevenlabs-key <キー>` で設定する必要がある |

**API キーの保存場所**：Gemini・Inworld・ElevenLabs 共通で、プラグインのデータディレクトリの `voice-readout.env` に `KEY=値` の形式でまとめて保存される（ファイルは `600`、ディレクトリは `700`）。バックエンドが増えてもこの1ファイルにキーが集約される設計。

データディレクトリは、フック実行時は Claude Code が渡す `${CLAUDE_PLUGIN_DATA}`、それ以外（ターミナルから `toggle.sh` を叩いたときなど）は `~/.claude/plugins/data/voice-readout-voice-readout/` に解決される。**以前はこの後者が `/tmp` にフォールバックしていた**ため、上の手順どおりターミナルでキーを登録すると共有ディレクトリにキーが書かれ、しかもフック側は別のファイルを読むので登録したキーが効かない、という状態になっていた（2026-07-25 に修正）。`/tmp` にフォールバックすることはもう無い。

> **API キーはチャットに貼らないこと。** 会話に書いた内容はトランスクリプトとして端末に保存され、モデルへの入力としても送られる。キーの登録だけは**ターミナルで直接コマンドを実行する**。切替のような他の操作はチャットからで構わない。

**セットアップ手順（Gemini）**：
1. [Google AI Studio](https://aistudio.google.com/) で API キーを取得する
2. **ターミナルで** `bin/toggle.sh gemini-key <キー>` を実行する
3. 「Gemini の TTS に切り替えて」で backend を切替（裏で `toggle.sh backend gemini` を実行）

**セットアップ手順（Inworld）**：
1. [Inworld Portal](https://platform.inworld.ai/) で API キーを取得する
2. **ターミナルで** `bin/toggle.sh inworld-key <キー>` を実行する
3. 「Inworld の TTS に切り替えて」で backend を切替（裏で `toggle.sh backend inworld` を実行）

**セットアップ手順（ElevenLabs）**：
1. [ElevenLabs](https://elevenlabs.io/) で API キーを取得する
2. **ターミナルで** `bin/toggle.sh elevenlabs-key <キー>` を実行する
3. 「ElevenLabs の TTS に切り替えて」で backend を切替（裏で `toggle.sh backend elevenlabs` を実行）

登録済みのキーを消すには `bin/toggle.sh <エンジン>-key clear`（例：`bin/toggle.sh gemini-key clear`）。シェルの履歴にキーを残したくない場合は、コマンドの先頭に空白を1つ入れて実行するか、`voice-readout.env` を直接編集する。

デフォルトの声・モデル・言語は環境変数で上書きできる：Inworld は `VOICE_READOUT_INWORLD_VOICE`（既定 `Olivia`、英語ネイティブの若い英国系女性声。Hina/Asuka/Sarah/Selene/Evelyn と聴き比べた上で2026-07-20に選定）/ `VOICE_READOUT_INWORLD_MODEL`（既定 `inworld-tts-1.5-mini`）/ `VOICE_READOUT_INWORLD_LANG`（既定 `ja`）、ElevenLabs は `VOICE_READOUT_ELEVENLABS_VOICE`（既定 `blVzlvngVR9lhf4Gflnk` = アカウントのマイボイス「アマテラステラス2」、middle-aged・ja-kanto）/ `VOICE_READOUT_ELEVENLABS_MODEL`（既定 `eleven_flash_v2_5`）。日本語に強い声を探したい場合は各社のダッシュボードで試聴して差し替える。

Gemini・Inworld・ElevenLabs いずれも、バックエンドが失敗した場合（キー未設定、API エラー、タイムアウトなど）は、その回だけ自動的にオンデバイスバックエンドで読み上げ直すフォールバックが入っているため、切り替えても無音になることはない。

**速度の実測（2026-07-20、4バックエンドを同一セッション内・同一文章で計測。読み上げ完了までの時間）**：

| 文章の長さ | オンデバイス | Gemini | Inworld | ElevenLabs |
|---|---|---|---|---|
| 短文（22字） | 8.8秒 | 20.8秒 | 15.9秒 | 14.6秒 |
| 中文（79字） | 16.8秒 | 39.5秒 | 26.0秒 | 25.1秒 |
| 長文（211字） | 34.4秒 | 59.9秒 | 49.9秒 | 46.5秒 |

オンデバイス比では、Gemini は1.7〜2.4倍、Inworld は1.5〜1.8倍、ElevenLabs は1.4〜1.7倍の時間がかかる。**この実測では ElevenLabs が3社中もっとも速く、僅差で Inworld、Gemini がはっきり遅い**という順序になった（公開ベンチマークでは Inworld Mini の方が Time-to-First-Audio は短いとされているが、ここでの計測は「音声が鳴り終わるまでの合計時間」で、両者の読み上げ速度・API往復のばらつきも含むため、単純な TTFA 比較とは前提が異なる点に注意）。文章が長くなるほど固定の通信コストの割合が薄まり、オンデバイスとの差は縮む傾向。この差が、許可確認の読み上げの既定をオンデバイスにしている（クラウド系にしていない）理由。

**クラウド系を使うなら、この実測ではまず ElevenLabs、僅差で Inworld を推奨**：どちらも Gemini より明確に速い。ElevenLabs は音声表現力（本家の音声タグ機能）でも定評があるため、速度と表現力を両立したい場合の第一候補になる。Gemini はテキスト内感情タグを試したいときの選択肢として残している。

（旧バージョンの実測値はテスト文言が異なり単純比較できないため、今回まとめて同条件で取り直した。長文の Gemini は初回計測時に `curl --max-time 20` のタイムアウトに引っかかって失敗しており、Gemini・Inworld・ElevenLabs とも45秒に緩めて計測している。）

## 読み上げ速度（全エンジン共通の指標）

速度は **`READOUT_SPEED` ひとつ**で決める。**1.0 = 毎分およそ300字**で、これはニュースを読むアナウンサーの標準的な話速にあたる。既定は **1.2**（Claude Code の出力は全部を集中して聞くものではなく、少し速い方が実用的なため）。「読み上げを1.3倍にして」「もう少しゆっくりして」のようにチャットで変えられる（裏で `toggle.sh speed 1.3`、範囲は 0.5〜2.0）。

**なぜエンジンごとの設定にしないのか**：4つのエンジンは素の話速がそもそも違うため、同じ「1.3」を各エンジンに設定しても速さは揃わない。同一文（147字）を無調整で読ませた実測（2026-07-25）：

| エンジン | 素の話速 | 300字/分との比 |
|---|---|---|
| gemini | 361字/分 | 1.20 |
| elevenlabs | 327字/分 | 1.09 |
| ondevice | 305字/分 | 1.02 |
| inworld | 271字/分 | 0.90 |

そこで各エンジンのキーは既定で `auto` とし、指標にこの差を吸収する係数を掛けて自動で決める：

| エンジン | キー | 係数 | 指標1.2 | 指標1.3 |
|---|---|---|---|---|
| ondevice | `TTS_RATE` | ×1.01 | 1.21 | 1.31 |
| inworld | `INWORLD_SPEAKING_RATE` | ×1.11 | 1.33 | 1.44 |
| elevenlabs | `ELEVENLABS_ATEMPO` | ×0.92 | 1.10 | 1.19 |
| gemini | `GEMINI_SPEED` | ×0.83 | 1.00 | 1.08 |

**厳密な倍率ではなく目安**である。同じ指標でも文章や声で数%はぶれるし、gemini だけは信号処理ではなくプロンプトでの速度指示なので追従が最も甘い。特定のエンジンだけ調整したいときは、そのキーに `auto` の代わりに数値を書けばそちらが優先される。

参考までに、オンデバイスで実測した体感の目安：指標1.0 が28.9秒（305字/分、アナウンサー相当）、1.4 が21.2秒（416字/分、早口な会話より少し速い）だった。

## 読み上げ速度の内訳（ElevenLabs）

ElevenLabs で「読み上げが遅い」と感じたときの調整方法は、**選んでいるモデルによって変わる**。2026-07-25 に同一文（55文字）・同一の声で実測した結果：

| 方法 | eleven_v3 | eleven_flash_v2_5 |
|---|---|---|
| API の `speed`（`ELEVENLABS_SPEED`） | **効かない**。1.0 / 1.2 / 1.4 とも同じ長さで、しかもエラーにならず 200 が返るため気づけない | 効く。ただし範囲は 0.7〜1.2 で、外すと 400（`invalid_voice_settings`） |
| オーディオタグ（`[rushed]` を本文の先頭に付ける） | わずかに効く（3回とも −4%前後）。`[fast-paced]` `[quickly]` `[speak quickly]` は効果なし | 未計測 |
| **`ELEVENLABS_ATEMPO`（生成後に ffmpeg で加速）** | **効く**。1.2 で −18%、1.3 で −25%、1.4 で −29% | 同じく効く |

素の速さはモデル自体でも違い、同じ文で v3 が 8.5〜8.7秒、flash が 7.4秒だった。

**推奨は `ELEVENLABS_ATEMPO`**。理由は3つ：モデルを選ばずに効く、`atempo` はピッチを変えないので声の印象が変わらない、そして**追加コストがほぼゼロ**——`ELEVENLABS_GAIN` が既定値でなければ生成後に ffmpeg を1回通っており、そこにフィルタを足すだけで済むため。値は `toggle.sh tune ELEVENLABS_ATEMPO 1.2` のように設定する（0.5〜2.0。範囲外はログに残して無視し、加工なしの音声で鳴らす）。

## クラウド読み上げのチャンク再生と継ぎ目マーカー

クラウド系（Gemini／Inworld／ElevenLabs）は、長い文章を一度に合成すると生成が終わるまで無音の待ち時間になる。そこで**文章を文単位でチャンクに分け、1つ目が出来たらすぐ喋り始め、喋っている裏で次を生成する**（先読み）。さらに、次のチャンクの再生開始を現在のチャンクの終わりに**少しかぶせて**呼び出すことで、`termux-media-player` の起動往復（実測で約2秒）を鳴っている音の裏に隠している。

| KEY | 既定 | 何が変わるか |
|---|---|---|
| `CLOUD_FIRST_CHUNK_CHARS` | 80 | **1つ目**のチャンクの長さ。短いほど喋り出しが早い |
| `CLOUD_CHUNK_CHARS` | 200 | 2つ目以降のチャンクの長さ。長いほど継ぎ目の回数が減る |
| `CLOUD_PLAY_LEAD` | 1.4 | 次のチャンクを何秒早くかぶせるか。**足りないと継ぎ目に隙間**が空き、大きすぎると語尾が食われる |

**チャンク区切りマーカー**（`CHUNK_MARKER`、既定 off）は、この継ぎ目を調整するための確認用の機能。on にすると各チャンクの末尾に短いキュー音（`assets/chunk-marker.wav`、0.78秒）が鳴る。

- **何のためにあるか**：音だけ聞いていると、聞こえた“間”が**文の切れ目でそう喋っただけ**なのか、**チャンクの受け渡しで空いた隙間**なのか区別できない。マーカーを入れると並びが `[本文][ピッ][間][次の本文]` になり、**ピッの直後に空いた間だけが継ぎ目の隙間**だと確定できる。`CLOUD_PLAY_LEAD` を上げるべきかどうかは、この区別が付いて初めて判断できる。どこで分割されたかを知る手段が他にないので、チャンク長を変えるときの目安にもなる。
- **使い方**：「チャンクマーカーをオンにして」で on（裏で `toggle.sh chunk-marker on`）。on の間はステータスラインの末尾に 🔔 が出るので、鳴っている理由が分からなくなることはない。確認が終わったら「チャンクマーカーをオフにして」で戻す。
- **コスト**：キュー音そのものが0.78秒×チャンク数ぶん再生時間を延ばす（これが主観的には支配的）。処理としては生成直後に ffmpeg で音声へ連結するため0.3〜0.45秒/チャンクかかるが、2つ目以降は前のチャンクを再生している裏で走るので体感には出ない（1つ目だけ喋り出しが0.3秒ほど遅くなる）。
- **実装（なぜ別再生ではなく連結なのか）**：キュー音を別ファイルとして再生すると、`termux-media-player` の起動往復（約2秒）がそのまま「本文とキュー音の間の空白」になり、何を測っているのか分からなくなる。生成したチャンク音声の末尾に連結して**同じ再生の続き**として鳴らすことで、この遅延を排除している。
- **対象**：クラウド系のチャンク再生経路のみ。オンデバイスや固定クリップには入らない。

## オンデバイス読み上げの長さ制限

オンデバイス（Termux:API 経由の Android TTS）には**1回の読み上げにつき 240 文字という上限**を設けている。エンジンに渡す前にテキスト長をチェックし、超えていればエンジンには触れない。

理由は Termux:API の既知の持病（[termux/termux-api#244](https://github.com/termux/termux-api/issues/244)、2018年から未修正）で、**長い読み上げの途中でエンジンが固まり、以降すべての termux-api コマンドがハングして、アプリを手動で強制停止するまで復旧しない**。チャンク分割・バックオフ・ウェイクロック・同時実行の排除など、こちら側でできる対策は 2026-07-20 に一通り試したがそれでも固まる。復旧にユーザーの物理操作（強制停止）が要る以上、**そもそも固まる領域に入らない**のが唯一まっとうな設計になる。この端末での実測では、同じ文章を3回読ませて 250 文字は毎回完走、336 文字は毎回同じチャンクで失敗した。240 文字（約45秒）は既知の安全圏の内側に余裕を持たせた値。

上限を超えたとき、**オンデバイスを選んでいる機能はオンデバイスのまま**、一文に要約して読み上げる。その際「**長文のため要約にします。**」という短い断りを先に流してから要約を伝えるので、聞き手は全文ではなく要約を聞いていることが分かる。この断りは**決まり文句なので事前に良い声（Gemini/Aoede）で録音した音声を同梱**していて（`assets/overflow-notice.wav`）、実行時はそれを `termux-media-player` で再生する（API キー不要）。同梱音声が無い環境では断り文をライブTTSで読み上げてフォールバックする。フル読み上げ・ファイル読み上げのどちらも同じ扱い：

| 機能 | オンデバイスで上限超過したとき |
|---|---|
| フル読み上げ（Stop・full） | 断りを添えて**一文要約に劣化**して読む。要約自体が240字を超える場合は240字に切り詰める |
| ファイル読み上げ（`speak-text.sh`） | 断りを添えて**一文要約に劣化**して読む（全文を読むには下記のとおりクラウド系へ切替） |

**上限超過でクラウドへ自動切替はしない**。オンデバイスを選んでいるのは利用者の明示的な選択であり、クラウドのAPIキーが登録されていてもそれを勝手に上書きはしない——クラウドの声を使いたい人は自分で切り替える、という考え方（機能ありきの一貫した扱い）。

クラウド系バックエンド（Gemini／Inworld／ElevenLabs）にはこの上限は無い。**長文を丸ごと読ませたい場合は、その機能のエンジンを自分でクラウド系に切り替える**（例：ファイル読み上げなら `toggle.sh backend-file elevenlabs`）。断り文は環境変数 `VOICE_READOUT_OVERFLOW_NOTICE` で差し替えられる（同梱クリップが無いときのライブ読み上げに使われる）。

## 長文パイプライン（冒頭を先に読み、裏で要約する）

上の「上限超過で一文要約に劣化」は、要約が出来上がるまで無音になるという弱点がある。要約は Haiku を `claude -p` で呼ぶので、CLI の起動込みで**十数秒**かかり、その間ずっと黙ったままになる。「反応がない、壊れた」と思わせるには十分な長さである。

`OVERFLOW_PIPELINE` を on にすると、その待ち時間を読み上げで埋める：

1. 応答の**冒頭 `OVERFLOW_OPENING_CHARS` 文字（既定150字）をそのまま即座に読み始める**（要約を待たないので無音がゼロになる）。区切りは直前の `。！？、` まで戻すので語の途中で切れない
2. その裏で**応答全体**を要約する（冒頭を除いた残りではなく全体。狙いは全体像であり、完全な文章から作ったほうが要約の質が高いため）
3. 事前録音クリップ「この後、全体を要約するね。」（`assets/summary-bridge.wav`）を挟む
4. 出来上がった要約を読む

3つの読み上げは**逐次**実行されるので、単一の TTS エンジンを取り合って固まることはない（並行するのはエンジンを使わない `claude` の呼び出しだけ）。冒頭を読むことでエンジンが温まり、後続がウォームスキップ（`WARM_SKIP_WINDOW`）の恩恵を受ける副次効果もある。

既定は off。実機での所要時間は `[info] pipeline timing:` のログ行（`要約 N秒 / 冒頭+ブリッジ N秒 / 要約前の空き N秒`）で確認でき、「要約前の空き」が大きければ `OVERFLOW_OPENING_CHARS` を増やす。

## 決まり文句の事前録音音声

内容が変わらない“決まり文句”は、毎回オンデバイスの機械的な声で合成する代わりに、**Gemini の良い声で一度だけ録音した WAV（`assets/*.wav`）を再生**している。狙いは、①毎回同じ良い声にする、②API キーもネットワークも使わない（録音済みなのでオフラインで鳴る）、③固まりやすい TTS エンジンを使わずに済ませる、の3つ。

- **対象の決まり文句**：上限超過の断り（`長文のため要約にします。`）／通知の定型フレーズ（`実行許可を求めています` `実行許可の確認が待っています` `入力を待っています` `確認が必要です`）／復旧メッセージ（`読み上げ、直ったみたいよ…`）。
- **声**：Gemini の `Aoede`。「20歳くらいの明るいアナウンサー」というキャラクター指定プロンプトを本文の前に付けて生成している（この指定文は読み上げられず、本文だけ喋る）。
- **再生する条件**：その機能のバックエンドが**オンデバイス（既定）のときだけ**クリップを再生する。クラウド系を選んでいる場合は利用者の声の選択を尊重してライブ合成する。クリップが同梱されていない環境では、いずれもライブ TTS にフォールバックする。
- **対象外**：ツール名を含む許可メッセージはツール名が可変なので、名前を言わない汎用クリップ `実行許可を求めています` で代用している。
- **録音の作り直し**：Gemini の API キーを設定した上で、テキストと声・キャラクター指定を与えて `assets/*.wav` を再生成できる（生成は開発時に手作業で行い、できた WAV をリポジトリに同梱する）。
